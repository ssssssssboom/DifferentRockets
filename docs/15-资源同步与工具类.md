# 15 · 资源同步与工具类

> 目标读者：刚接手 DifferentRockets 的中国开发者。
> 本文覆盖 `core/src/com/differentrockets/util/` 下的五个工具类（`Res`、`AtlasPack`、`Json`、`Xml`、`Vec2d`）以及应用入口 `game/DRGame.java`，重点讲清玩家可编辑资源目录的「双根策略 + 版本化同步」机制。所有事实均来自源码，引用格式为 `文件名:行号`（相对 `game/core/src/com/differentrockets/`，除非特别注明）。

---

## 1. 全景：这套机制解决什么问题

DifferentRockets 的核心卖点之一是「玩家可改资源」：贴图、XML 配置、lua 零件脚本都不是锁死在 APK 里的，而是在首次运行时拷贝到外部存储，让玩家直接编辑（`Res.java:19-21`）。这带来三个工程问题：

1. **放哪里**——`/sdcard` 共享目录玩家能看到，但 Android 需要存储权限；权限没给时游戏也得能跑。→ 双根策略（§2）。
2. **APK 里的默认文件怎么枚举**——Android 的 `AssetManager.list()` 在一批设备上返回空数组，拷贝循环跑零次，目录建了却是空的。→ 硬编码 manifest（§3）。
3. **游戏更新后，玩家目录里的旧默认文件怎么升级**——玩家没改过的文件应跟随新版默认更新，玩家改过的绝不能覆盖。→ 版本化同步算法（§4）。

任何目录都不可写时，所有资源查找优雅回退到 APK 内置 assets（`Res.java:27-28`）。

## 2. Res 的双根策略

### 2.1 两个候选根

`Res` 维护三个静态字段（`Res.java:32-35`）：

| 字段 | 含义 | Android 上的路径 |
|---|---|---|
| `sharedRoot` | 目标根：共享外部存储 | `/storage/emulated/0/DifferentRocket/` |
| `privateRoot` | 回退根：app-private 外部目录 | `Android/data/<pkg>/files/DifferentRocket/` |
| `root` | 当前生效的根（二选一） | — |

桌面端不区分双根：`sharedRoot = privateRoot = ../DifferentRocket/`（工作目录 `core/assets` 的父级，这样玩家副本永远不会落进 Android assets 树、被打进 APK，`Res.java:132-137`）。

### 2.2 为什么用反射拿 `getExternalStorageDirectory()`

`sharedRoot` 的基路径来自 `android.os.Environment.getExternalStorageDirectory()`，**不是** `Gdx.files.getExternalStoragePath()`——后者自 libGDX 1.9.10 起返回的是 app-private 的 `getExternalFilesDir()`，玩家根本看不见（`Res.java:10-12`、`Res.java:116-121`）。

之所以走反射（`Class.forName("android.os.Environment")`）而不是直接调 API：core 模块编译路径里没有 `android.jar`（`Res.java:141`）。`sharedBase()`（`Res.java:142-161`）的防御逻辑：

- 反射抛异常 → 记录 error 日志，`p` 保持 null；
- 路径为 null/空/不以 `/` 开头 → 视为可疑，强制回退到 `/storage/emulated/0`（`Res.java:151-155`）；
- 非标准路径（多用户 / work profile 场景）也照常使用，仅打日志提示（`Res.java:156-158`）。

### 2.3 选根与探测

`populate()`（`Res.java:187-215`）每次执行都重新选择最优根：

1. `probeWritable(sharedRoot)` 可写 → 用共享根；
2. 否则 `privateRoot` 存在且可写 → 回退 app-private，并打 WARNING 说明会在每次 resume 重试共享根（`Res.java:193-199`）；
3. 都不可写 → `external = false`，全部资源查找回退内置 assets（`Res.java:200-205`）。

`probeWritable()`（`Res.java:218-230`）是「`mkdirs` + 写一个 `.probe` 文件再删掉」——注释明确指出这是唯一可靠的可写性测试（`Res.java:217`）。任何异常一律返回 false。

首次从 private 切换到 shared 时触发 `migrateToShared()`（`Res.java:238-250`）：把 app-private 根下玩家已有的文件**只补缺失**地递归拷到共享根（`copyMissing`，`Res.java:252-264`）——共享根里已有的文件不覆盖（玩家编辑优先），private 副本原地保留（应用仍可读自己的私有目录）。

### 2.4 resume 时重试与热切换

`refresh()`（`Res.java:170-180`）在每次 app resume 时重跑 `populate()`，这样用户在系统设置里授予 `MANAGE_EXTERNAL_STORAGE` 后**无需重启应用**即可生效。仅当活跃根发生变化（内置回退 → external，或 private → shared）时返回 true。

调用链在 android 模块：`AndroidLauncher.onResume()` 里 `Res.refresh()` 返回 true 时，先 dismiss 权限对话框，再调 `game.reloadResources()`（`game/android/src/com/differentrockets/android/AndroidLauncher.java:46-51`）。

### 2.5 资源查找入口

| 方法 | 行为（`Res.java:566-590`） |
|---|---|
| `usingExternal()` | 玩家根是否可用 |
| `asset(name)` | 贴图/XML：玩家根 `assets/` 下存在则用之，否则回退 `Gdx.files.internal(name)` |
| `modDir()` | 玩家 `mod/` 目录；回退时为内置 `mods/` |
| `modFile(name)` | 单个 mod 文件：玩家副本优先，内置兜底 |

## 3. 硬编码 manifest：为什么不枚举 assets

`ASSET_FILES`（25 个贴图/XML，`Res.java:45-73`）和 `MOD_FILES`（33 个 lua，`Res.java:75-109`）是**显式写死**的两张清单。注释（`Res.java:38-43`）记录了教训：原先用 `Gdx.files.internal("").list()` 枚举，但 Android 的 `AssetManager.list()` 在 APK asset 根目录上一批设备返回空数组——拷贝循环执行零次，玩家目录被创建却永远是空的。硬编码清单在所有设备上行为确定。

防呆措施：`checkManifest()`（`Res.java:531-554`）在桌面/dev 环境做反向校验——桌面端目录列表是可靠的，逐个比对内置 assets 里的 `.png`/`.xml` 和 `mods/` 下的 lua 是否都在清单里，漏了输出 `MISSING FROM MANIFEST: ...`。该方法由 SmokeScreen 调用（`Res.java:528-530`），新增资源忘登记时能在开发期暴露。

## 4. 版本化同步算法（round 10 + round 16）

这是 `Res` 最复杂的部分。目标：**玩家没碰过的出厂文件跟随游戏版本自动升级；玩家改过的文件永远保留**。

### 4.1 目录布局

玩家根下每个资源组（`assets`、`mod`）都有一个 `.defaults/` 影子目录，存放**上一次运行时的出厂字节**（`Res.java:22-24`），另附 `_README.txt` 用中英文警告玩家勿改（`Res.java:415-418`）：

```
DifferentRocket/
  assets/            ← 玩家可编辑的贴图与 XML
    .defaults/       ← 参考副本（自动更新判定用，勿改）
  mod/               ← 玩家可编辑的 lua 脚本
    .defaults/
```

### 4.2 主流程

`copyDefaults()`（`Res.java:517-523`）→ `syncTree()`（`Res.java:315-320`）→ 对 `assets`、`mod` 两组各跑一次 `syncGroup()`（`Res.java:322-425`）。`syncGroup` 分两个 pass：

**Pass 1（对旧 `.defaults` 做比较/替换，`Res.java:329-405`）**：对 manifest 中每个文件 `X`，按优先级判定：

| # | 条件 | 动作 | 计数/日志 |
|---|---|---|---|
| 1 | `X` 不存在 | 从内置 assets 拷贝 | `copied`（`Res.java:341-351`） |
| 2 | `X` 与新默认字节相等 | 不动 | `kept-current`（`Res.java:362-365`） |
| 3 | `X` 与旧 `.defaults/X` 字节相等（非首次部署且 def 存在） | 玩家从未改过 → 覆盖为新默认 | `auto-updated`（`Res.java:366-371`、`381-390`） |
| 4 | `X` 的 SHA-1 命中 `KNOWN_OLD` | 可证明是旧版本出厂副本 → 覆盖 | `auto-updated`（`Res.java:372-380`） |
| 5 | 是 `.lua` 且版本头严格更旧 | 备份一次后覆盖（见 §4.4） | `auto-updated`（`Res.java:391-393`） |
| 6 | 其余 | 保留：首次部署记 `kept-unknown`，否则记 `kept-player` | （`Res.java:394-404`） |

判定 3 和 4 共用 `legacyFactory` 标志：先比 `.defaults`，不中再算 SHA-1 查 `KNOWN_OLD`（key 形如 `"mod/physics.lua"`，`Res.java:373`）。

**Pass 2（强制刷新 `.defaults`，`Res.java:406-421`）**：整个删除重建 `.defaults/`，把当前 bundle 的默认文件逐一拷入，再写 `_README.txt`。注意顺序——**所有比较都基于旧的 `.defaults` 做完之后才刷新**（`Res.java:308-310`）。

收尾时 `copyDefaults` 打一行汇总日志：`copied / auto-updated / kept-current / kept-player / kept-unknown / failed` 六个计数（`Res.java:519-522`）。每个文件级别的失败都单独记 error，单文件失败不拖垮整组（`Res.java:422-424`）。

### 4.3 KNOWN_OLD：版本化机制出现之前的历史包袱

`.defaults` 机制是 round 10 才引入的，更早安装的玩家目录里没有影子副本可比。`KNOWN_OLD`（`Res.java:273-296`）内置了若干**历史出厂文件的 SHA-1**，命中即证明是未修改的旧出厂副本，即使首次部署也能安全覆盖：

- `mod/physics.lua`：round-8 出厂版（重构验证过）与 round-9 版（含重复的 gimbal 文档段落，随 round-9 APK 发布），两个哈希；
- 六个带 gimbal 的引擎脚本（`engine-0` ~ `engine-4` + `ion-0`）：round-8 时六个文件字节完全相同（cp 同步过），共享同一组两个哈希（含同步前的早期变体）；
- `mod/flame.lua`：round-8 出厂版（三角锥形尾焰，粒子化之前）。

### 4.4 版本头回退识别 + .player-bak 备份（round 16）

`KNOWN_OLD` 只覆盖了三个脚本，round-8/9 时代的其他出厂 lua 在首次部署时既不等于新默认、又无 `.defaults` 可比，会永远卡在 `kept-unknown`。`replaceOlderFactoryLua()`（`Res.java:441-466`）补上这个洞：

1. 用 `LuaScript.versionOf()` 分别解析玩家副本与内置默认的版本头——每个出厂 lua 前 5 行内有 `-- vX.Y.Z` 注释，取第一个以 `--` 开头、去空格后以 `v`+数字开头的注释（`game/LuaScript.java:45-65`）；
2. 任一解析失败（返回 `"?"`）→ 放弃，走正常 `kept-player` 路径（`Res.java:451`）；
3. 玩家版本 **≥** 内置版本 → 放弃（`Res.java:452`）；
4. 玩家版本**严格更旧** → 判定为「旧出厂脚本（可能带玩家在旧基础上的修改）」：
   - 若 `<name>.player-bak` 不存在，先把玩家副本备份过去——**只保留第一代备份**，已存在则不覆盖（`Res.java:454-455`）；
   - 用内置默认覆盖玩家文件，日志记录 `v旧 -> v新` 与备份位置（`Res.java:456-460`）。

版本比较 `compareVersions()`（`Res.java:474-483`）：点分数字元组逐段比 int，首个不同段定胜负；公共段全等时**更长的元组更大**（`"2026.07.21" < "2026.07.22.2"`，`"1.2" < "1.2.1"`）；不可解析的段按 0 计（`versionSeg`，`Res.java:485-491`）。

> 注意 round 16 路径与 round 10 路径的语义差别：判定 3/4 覆盖的是「**字节级未动过**的旧出厂文件」；判定 5 覆盖的可能是「玩家**在旧出厂基础上改过**的文件」——所以才需要 `.player-bak` 备份兜底。

### 4.5 测试钩子

`syncTreeForTest(String absoluteRoot)`（`Res.java:507-509`）公开了 `syncTree`，可对任意目录跑一遍同步，便于单元测试验证六种计数。

## 5. AtlasPack：TexturePacker 图集解析

`AtlasPack`（110 行）是 CodeAndWeb TexturePacker **XML 格式**图集的迷你解析器，不用 libGDX 自带的 `.atlas` 格式加载器（`AtlasPack.java:12-18`）。

### 5.1 构造

`new AtlasPack(FileHandle xmlFile)`（`AtlasPack.java:25-45`）：

1. `XmlReader` 解析 XML，根节点的 `imagePath` 属性指向同目录贴图，`new Texture(img)` 加载并设 `Linear` 过滤（`AtlasPack.java:27-30`）；
2. 遍历子节点 `<sprite n=".." x=".." y=".." w=".." h=".." [r="y"]/>`，每个 sprite 建三个索引：`regions`（`TextureRegion`）、`rects`（打包矩形 `x,y,w,h`）、`rotated`（是否旋转存放）（`AtlasPack.java:31-41`）；
3. 坐标系约定：y 从左上角量（`AtlasPack.java:12`）；
4. 解析失败抛 `RuntimeException("Failed to parse atlas ...")`（`AtlasPack.java:42-44`）——图集是硬依赖，启动期宁可 crash 也不带病运行。

### 5.2 旋转 sprite 的处理

`r="y"` 表示该 sprite 在图集中被顺时针转了 90°（TexturePacker 省空间约定）；XML 里的 `w/h` 是**打包后**的矩形，所以未旋转的原始 sprite 实际是 `h×w`（`AtlasPack.java:14-17`）。

- `isRotated(name)` 查询某 sprite 是否旋转存放（`AtlasPack.java:70-73`）；
- `extractUnrotated(name)`（`AtlasPack.java:80-107`）把 sprite 抠成独立 `Texture` 并**逆时针 90° 还原**为正向：从图集 Pixmap 扣出 `w×h` 子图，旋转时逐像素做 `O(X,Y) = P(w-1-Y, X)`，输出 `h` 宽 `w` 高的新 Pixmap。返回值由调用方负责 dispose；未知名称返回 null。物理/建造界面需要直接拿正立贴图时使用。

### 5.3 大小写不敏感查找

XML 里 sprite 名混用 `.png`/`.PNG`，`find()` 与内部 `canonical()` 都是先精确匹配、失败再全表小写比对（`AtlasPack.java:47-67`）。

`dispose()` 只释放底层 `Texture`（`AtlasPack.java:109`）。

## 6. Json：存档系统的最小 JSON 实现

`Json`（223 行）是一个 pretty-print 写入器 + 小型递归下降解析器，刻意不依赖 gdx-json——注释说明是为了规避其在 Android 上的怪癖，只实现存档系统需要的子集（`Json.java:6-9`）。

### 6.1 Writer

链式 API（`Json.java:13-79`）：

- `obj()/endObj()`、`arr()/endArr()` 开闭作用域，`indent` 维护缩进，`needComma` 状态机自动补逗号与换行（`Json.java:34-37`）；
- `key(k)` + `val(...)` 或一步 `set(k, v)`（重载 String/double/int/long/boolean）；
- 细节：`val(double)` 对 NaN/Infinity 写 `0`（`Json.java:49`）——存档里不允许出现非法 JSON 数字；
- `quote()` 转义 `"`、`\`、`\n`、`\r`、`\t`，其余控制字符（<32）转 `\uXXXX`（`Json.java:60-76`）；
- 构造参数 `pretty=false` 可关格式化（`Json.java:19-20`）。

### 6.2 解析

`Json.parse(text)`（`Json.java:125-132`）要求**根必须是 object** 且无尾随内容，否则抛 `RuntimeException`。返回值模型：

- `JObj`：不用 HashMap，而是 `keys` + `vals` 两个平行 List（`Json.java:106-108`）——保留键的插入顺序，`get` 是 `indexOf` 线性查找（键少，无所谓）；
- `Value.o` 实际类型为 `String / Double / Boolean / List<Value> / JObj / null`（`Json.java:83`）；
- 一组带默认值的容错 getter：`asNum(def)` 会把数字字符串也尝试 parse（`Json.java:93-97`），`asBool`、`getStr/getNum/getInt/getBool/getObj/getArr` 同理（`Json.java:99-122`）。存档字段缺失或类型漂移时不会崩，直接拿默认值。

Parser（`Json.java:134-222`）是教科书式递归下降：`parseValue` 按首字符分派；字符串支持全部标准转义含 `\uXXXX`；`parseNum` 用字符集 `"0123456789.eE+-"` 扫描再 `Double.parseDouble`——**所有数字统一解析为 Double**，没有 int/long 之分。

## 7. Xml：一个补丁方法

`Xml`（14 行）只有一个静态方法 `getDouble(Element, name, def)`：libGDX 的 `XmlReader.Element` 有 `getIntAttribute`/`getFloatAttribute` 却没有 double 版，这里用 `getAttribute` 拿字符串后 `Double.parseDouble`，缺属性或解析失败都返回默认值（`Xml.java:5-13`）。游戏 XML 配置里的物理常数需要 double 精度，全部经由它读取。

## 8. Vec2d：宇宙坐标的双精度向量

`Vec2d`（30 行）是可变（mutable）double 精度 2D 向量，用于**宇宙坐标**——Box2D 的 `Vector2` 是 float，在太阳系尺度下精度不够（`Vec2d.java:3`）。API 刻意模仿 libGDX `Vector2`：`set/add/sub/mul/len/len2/dist/dist2/nor/angleRad`，全部就地修改并返回 `this` 支持链式调用；`fromAngle(rad, len)` 由极角构造（`Vec2d.java:11-29`）。`nor()` 对近零向量（<1e-12）静默跳过，避免除零（`Vec2d.java:23`）。轨道预测、行星位置、>4x 加速下的预计算轨道跟随等长距离计算都基于它。

## 9. DRGame：启动流程与资源热重载

`DRGame extends Game`（96 行）是 libGDX 应用入口，持有全局共享对象（`DRGame.java:17-27`）：

| 字段 | 用途 |
|---|---|
| `batch` / `shapes` | 全局 `SpriteBatch` / `ShapeRenderer` |
| `font` / `bigFont` | 全局字体；`FONT_SCALE = 1.75f`（owner 要求更大的按钮/触控目标，`DRGame.java:14-15`），bigFont 固定 2.5x（`DRGame.java:36-38`） |
| `ui` | UI 辅助类 |
| `shipSprites` / `planetSprites` / `runtimeSprites` | 三张 `AtlasPack` 图集 |
| `world` | `GameWorld` 实例（整个游戏世界） |

### 9.1 create() 启动顺序

`create()`（`DRGame.java:29-51`）严格按依赖顺序初始化：

```
Res.init()            ← ① 资源根就绪（首运行拷贝默认资源）
batch/shapes/font/ui  ← ② 渲染基础设施
PartList.load()       ← ③ 零件定义（依赖 Res 的 XML）
ModManager.init()     ← ④ lua mod 系统（依赖 Res 的 mod/ 目录）
三张 AtlasPack        ← ⑤ 图集（经 Res.asset() 玩家副本优先）
new GameWorld()       ← ⑥ 世界
setScreen(MenuScreen) ← ⑦ 进主菜单
```

### 9.2 屏切换

`DRGame` 本身只在启动时 `setScreen(new MenuScreen(this))`（`DRGame.java:50`）。运行时三屏之间的切换分散在各 Screen 内：

- `MenuScreen` → `EditorScreen`（新建/编辑火箭）或 `SandboxScreen`（直接进沙盒）（`ui/MenuScreen.java:44,50`）；
- `EditorScreen` → `SandboxScreen`（发射，`ui/EditorScreen.java:545`）或退回 `MenuScreen`（`ui/EditorScreen.java:254,912`）；
- `SandboxScreen` → `MenuScreen`（`ui/SandboxScreen.java:209`）。

另有 `setTargetHeading/getTargetHeading` 两个便捷委托直通 `world`，供转向环 UI 使用（`DRGame.java:78-80`）。

### 9.3 reloadResources()：免重启热重载

配合 §2.4 的 resume 重试，`reloadResources()`（`DRGame.java:58-76`）在资源根切换后**不重启应用**重读一切：

1. `world.save()` —— 先保存当前会话；
2. `PartList.load()` + `ModManager.reset()` —— 重读零件定义与 lua mod；
3. `FlameScript / TerrainScript / PhysicsScript / JointScript.invalidate()` —— 四个特殊脚本强制下次访问时重读文件（invalidate 的实现见 `LuaScript.java:39-43`）；
4. 三张图集先 `dispose()` 再从新根重建；
5. `world.dispose()` → `new GameWorld()` → `world.load()` —— 世界重建并恢复刚才的存档。

### 9.4 dispose()

`dispose()`（`DRGame.java:82-95`）：先 `world.save()`（退出前保底存档）再 `world.dispose()`，然后逐个释放 batch/shapes/font/ui 与三张图集（`runtimeSprites` 做了 null 检查），最后 `super.dispose()`。
